## 슬라이드별 말할 말

### 1. 표지 (20초)
"Base AI Agent가 장애 유형을 고르고 대응 매뉴얼을 찾는 그 부분을 개선했습니다.
 2분은 무엇을 고쳐서 어떤 결과가 나왔는지, 3분은 그래프와 MCP, RAG 코드를 설명하겠습니다."

### 2. 무엇을 고쳤나 (1분)
- "기존 판정은 키워드 규칙을 순서대로 보다가 **처음 맞는 것**을 고르는 방식이었습니다.
  규칙 순서와 증상 우선순위가 무관하고, 질의문은 아예 보지 않았습니다.
  기준선을 먼저 재니 12문항 중 4개를 틀렸습니다."
- "네 축을 손봤습니다. 판정을 RAG로 바꾸고, 라우팅 공백을 고치고, 데이터를 늘리고,
  이걸 측정할 하네스를 만들었습니다."
- 말할 말: "판정 하나를 바꾼 게 아니라, 판정의 근거를 남기고 측정할 수 있게 바꾼 게 이번 과제입니다."

### 3. 결과 (40초)
- "같은 입력, 같은 조건에서 두 번 돌렸습니다. 정확도 0.3250에서 0.8500, E2E 5문항 1/5에서 5/5,
  회귀 질의 3/10에서 10/10입니다."
- "비용은 늘지 않았습니다. 대신 분류당 32.43ms가 늘었습니다 — 임베딩을 한 번 불러서 그렇습니다."
- **한계부터 말한다**: "데이터 확장은 정확도를 올리지 못했습니다. 커버리지만 좋아졌습니다.
  margin 게이트는 2문항을 아꼈습니다. keyword 폴백률은 15.00%였고, 그 6건은 동점 케이스였습니다."

### 4. Agent Graph 구성 (1분)
- "그래프는 route에서 plan, gate를 지나 research를 하고, replan_check에서
  '정보가 부족하다'고 판단해 런북을 추가로 조회합니다. write에서 validate를 거칩니다."
- "제가 손댄 건 **replan_check가 장애 유형을 정하는 한 줄**입니다. 나머지 그래프는 그대로입니다."
- "여기서 판단을 바꾸면 런북 조회(그래프 밖)와 답변 작성(그래프 안)이 같이 바뀌어서,
  근거가 안 보이는 변경이 됩니다. 그래서 선택 근거를 state에 남기고 SSE로 내보냈습니다."
- 말할 말: "제 판정을 고친 위치가 어디인지 화면으로 보이게 해뒀습니다."

### 5. RAG 코드 (1분)
- "입력은 네 블록입니다: 사용자 질문, 시스템, 상태, 알림. 질의문을 넣는 이유는
  기존 오분류 2개가 '질의를 안 본 것'이었기 때문입니다."
- "판정은 5분기입니다. 인덱스가 없거나, 임베딩이 실패하거나, 점수가 0.50 미만이면,
  또는 1위와 2위 점수 차이가 0.03 미만이면 keyword로 내려갑니다.
  **RAG가 확신하지 못하면 예전 동작 그대로**입니다. 이 게이트가 있어야 기존 동작이 안 깨집니다."
- 캡처를 가리키며: "이게 실제 SSE 출력입니다. 어느 런북을 골랐는지, 점수가 얼마인지,
  1·2위 차이가 얼마지가 그대로 나옵니다."

### 6. MCP 코드 (1분)
- "모니터링 조회와 런북 조회는 MCP ops 서버를 통해서만 합니다. Tool이 상태를, Resource가 런북을,
  Prompt가 분석 절차를 줍니다. stdio subprocess로 붙습니다."
- "문서 서버(mcp_server_docs)는 decoy라서 쓰지 않습니다."
- "데이터 파일 선택은 `agent/data_profile.py` 한 곳에서만 합니다. 경로가 다섯 곳에 흩어져 있으면
  시스템만 늘고 실제로 조사하는 대상은 여섯 개로 잘립니다. 가짜 확장이 됩니다."
- "RAG는 의존성 주입으로 넘깁니다. 노드가 환경변수를 직접 읽지 않습니다."
- "LangSmith는 노드에 `@traceable`을 걸어뒀고 환경변수로 켭니다. 실 API 키 없는 환경이라
  이번 실행에서는 트레이스 캡처를 못 했습니다."

## 예상 질문과 답

**"라벨을 직접 만들었는데 정확도가 의미가 있나요?"**
라벨을 측정 전에 동결했고(동결 시각·해시 기록), 카테고리별로 나눠서 보고했습니다.
질의 의존도가 높은 20문항을 따로 두고 카테고리별 정확자를 함께 냈습니다.
전체 수치를 일반화 성능으로 쓰지 않습니다. 실제 티켓 기반 라벨은 다음 단계로 남겼습니다.

**"RAG가 느려지는데 왜 도입했나요?**
분류 1건당 임베딩 1회 호출이니 +32.43ms입니다. 실서버 요청 전체로도 약 9% 수준입니다.
그 비용으로 40문항 기준 오분류 11개가 줄었고, keyword 경로에만 남던 결함도 사라졌습니다.

**"데이터 확장이 효과가 있었나요?**
분류 정확도에는 없었습니다. 그대로 기록했습니다. 대신 40문항이 조회한 모니터링 80회 중
데이터가 없어 못 본 15회가 0회가 됐습니다.

**"폴백이 많아서 RAG가 안 쓰는 거 아닌가요?**
40문항 중 6건(15.00%)만 keyword로 내려갔습니다. 그 6건은 1·2위 유사도 차이가
0.0155, 0.0000처럼 사실상 동점이었던 경우입니다.

**"LangSmith는요?**
`@traceable`을 노드에 걸고 `LANGCHAIN_TRACING_V2`로 켜도록 해뒀습니다.
이 환경에는 API 키가 없어 실제 트레이스를 캡처하지 못했습니다.
