### 2. 문제 (50초)
- "기존 판정은 키워드 규칙을 순서대로 보다가 **처음 맞는 것**을 고르는 방식이었습니다."
- "규칙 순서가 증상 우선순위와 무관합니다. 타임아웃과 CPU가 섞이면 CPU가 먼저 잡혔습니다."
- "질의문은 아예 안 봤습니다. 디스크 부족이라고 해도 지연 알림에 가려서 지연으로 분류됐습니다."
- "고치기 전에 기준선을 먼저 재니 12문항 중 4개가 어긋났습니다. 그 4개가 전부 코드 위치로 설명됐습니다."

### 3. 개선한 기능 (40초)
- "네 축을 손봤습니다. 판정을 RAG로 바꾸고, 라우팅 기준을 넓히고, 데이터를 늘리고, 이걸 측정할 수 있게 만들었습니다."
- "라우팅은 마지막에야 발견했습니다. 매뉴얼이 알려준 테스트 질의 7개가 chat으로 떨어져 있었어요."

### 4. 결과 (30초)
- "같은 입력, 같은 조건에서 두 번 돌렸습니다. 정확도 0.3250에서 0.8500, 회귀 질의 3/10에서 10/10입니다."
- "비용은 늘지 않았습니다. 대신 분류당 32.43ms가 늘었어요 — 임베딩 한 번 불러서 그렇습니다."
- **한계를 먼저**: "데이터 확장은 정확도를 0 올렸습니다. 커버리지만 좋아졌습니다. margin 게이트는 2문항을 아꼈습니다."

### 5. Agent Graph (50초)
- "그래프는 그대로 두고, replan_check가 런북을 정하는 그 한 줄만 바꿨습니다."

- "그래서 근거를 health·metadata·SSE 세 곳에 남겼습니다."

### 6. RAG 코드 (50초)
- "입력은 네 블록입니다 — 질문, 시스템, 상태, 알림. 질의문을 넣는 이유는 기존 오분류 2개가 질의를 안 본 것이라서입니다."
- "판정은 5분기입니다. 인덱스가 없거나 임베딩이 실패하거나 점수가 0.50 미만이면, 또는 1위와 2위 차이가 0.03 미만이면 keyword로 내려갑니다."
- "이 게이트가 안전장치입니다. RAG가 확신하지 못하면 예전 경로로 돌아가서 기존 동작이 깨지지 않습니다."

## 예상 질문과 답

**"라벨을 직접 만들었는데 정확도가 의미가 있나요?"**
라벨을 측정 전에 동결했고(동결 시각·해시 기록), 카테고리별로 나눠서 보고했습니다.
질의 의존도가 높은 20문항을 따로 두고 카테고리별 정확자를 함께 냈습니다.
전체 수치를 일반화 성능으로 쓰지 않습니다. 실제 티켓 기반 라벨은 다음 단계로 남겼습니다.

**"RAG가 느려지는데 왜 도입했나요?**
분류 1건당 임베딩 1회 호출이니 +32.43ms입니다. 실서버 요청 전체로도 약 9% 수준입니다.
그 비용으로 40문항 기준 오분류 11개가 줄었고, keyword 경로에만 남던 결함도 사라졌습니다.

**"데이터 확장이 효과가 있었나요?**
분류 정확도에는 없었습니다. 그대로 기록했습니다. 대신 40문항이 조회한 모니터링 80회 중
데이터가 없어 못 본 15회가 0회가 됐습니다.

**"폴백이 많아서 RAG가 안 쓰는 거 아닌가요?**
40문항 중 6건(15.00%)만 keyword로 내려갔습니다. 그 6건은 1·2위 유사도 차이가
0.0155, 0.0000처럼 사실상 동점이었던 경우입니다.

**"LangSmith는요?**
`@traceable`을 노드에 걸고 `LANGCHAIN_TRACING_V2`로 켜도록 해뒀습니다.
이 환경에는 API 키가 없어 실제 트레이스를 캡처하지 못했습니다.
