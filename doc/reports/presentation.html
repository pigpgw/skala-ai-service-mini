문제

장애 유형을 고르는 부분이 틀리고 있었다

판정 로직이 한 함수에 압축돼 있었고, 규칙 순서가 곧 결과였습니다.
# agent/graph.py::_classify_incident_type()
latency → pool → cpu → memory → timeout
  → network → disk → down
# 순서대로 보다가 "처음 맞는 것"을 선택
  • 규칙 순서가 증상 우선순위와 무관
    CPU가 timeout보다 앞에 있어, 타임아웃 질의가 cpu-spike가 됨
  • 질의문을 아예 보지 않음
    "디스크 부족" 신고가 지연 알림에 가려 high-latency가 됨
  • 매칭 실패 시 무조건 db-down
    "아무 장애나 db-down 대응을 내놔라"

해석

좋았던 것과, 안 좋았던 것

데이터 확장은 정확도를 올리지 못했다

base 34/40 ≡ extended 34/40 — 문항 단위로 동일. 라벨이 질의에 증상을 적어 둬서 RAG가 질의만 읽어도 맞고, 시스템 알림은 중복 신호가 됐습니다. 그래서 "확장으로 정확도 상승"이라고 쓰지 않았습니다.

대신 조사 커버리지(unknown) 18.75% → 0%

margin 게이트는 2문항을 아꼈다

임계값을 0.00으로 풀면 36/40이 되지만, 그 2문항은 1·2위 유사도 차이가 0.0155·0.0000인 동점입니다. 1단계에서 정답이 뒤집힌 사례도 이런 동점이었습니다.

0.03 유지 + 비용 2문항 기록

keyword 폴백은 6/40 (15.00%) — 1·2위 유사도 차이가 0.0155·0.0000인 동점이었던 경우

RAG의 비용은 임베딩 1회 호출입니다. 분류 1건당 +32.43ms, 실서버 요청 전체로는 +68.97ms — 요청 시간의 약 9% 수준이었습니다.
